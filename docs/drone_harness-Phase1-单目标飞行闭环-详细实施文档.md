## 2026-09-26 后续三阶段改造：当前生效设计

**目标与范围。**继续使用一个持续运行的 `drone_harness`、同一个多模态 VLM 和现有 `runtime → agent_loop → tool_dispatcher → flight → Px4Controller` 链路。用户希望模型自己决定何时看图：新目标与每次飞行动作后都不自动插入 RGB-D，模型通过 `observe(prompt)` 主动取得画面，再由**同一个主 VLM**直接看 RGB 图片、读取程序计算的深度摘要并决定后续工具调用；没有“第二个视觉 VLM 先写图像描述”的链路。`forward` 的执行限额则始终由程序在调用时重新读取深度图、按几何规则计算，不依赖模型估距或最近一次 `observe` 的旧上限。保留原有 PX4 状态、Offboard 握手、动作超时、人工介入、悬停交接与真机 HITL；不新增第二个模型、ROS 节点或飞行守卫。用户自行做后续真实仿真；这里先做离线验证，不宣称 19 米位置指令已经通过实测安全验收。

**阶段 1：悬停后恢复动作。**仅仿真允许已连接、已解锁、确认在空中且处于 `AUTO.LOITER` 的控制器进入原 `start_position_hold` 流程，由该流程切回 `OFFBOARD` 后执行本次位移；真机仍要求原有 `OFFBOARD` 前提。不在 `forward` 或垂直工具外另造飞控模式切换链。以假控制器验证 LOITER 恢复、未解锁/不在空中拒绝及原异常交接。

**阶段 2：增加 `up(distance_m)` 与 `down(distance_m)`。**二者只接收有限、非布尔且大于零的米数，单次不超过当前 profile 的 `max_vertical_move_m`（当前仿真 10 米、实机 2 米）；反复调用没有累计 10 米高度封顶。要求已确认在空中、PX4 已连接且已解锁；仿真可从 `AUTO.LOITER` 经原握手恢复，实机仍按原模式/HITL 限制。`up`/`down` 仅把 NED 的 z 分量分别设为负/正后复用原 `move`，不检查上下方向障碍；原 `move` 的近地 0.3 米下界、位姿、超时、介入和悬停逻辑继续生效。模型可见工具变为六种飞行动作，schema 要说清上述单次限制和下降不等于降落；所有新增函数保持简洁中文注释。

**阶段 3：按需 `observe(prompt)` 的消息合同。**模型可见工具再增加一个**非飞行动作** `observe`，必填去掉首尾空白后 1–1000 字符的字符串 `prompt`，用于说明本次要查看什么。新任务仅向 VLM 发送系统提示词和用户文字，并清除上一任务缓存的观测与深度规则；第一张图也须由 VLM 调用 `observe` 才取得。工具沿用现有 controller 的 RGB-D 等待/配对和深度规则计算，先追加与工具调用 ID 对应的普通工具结果（观测号、是否取到 RGB、深度是否有效、错误原因等脱敏元数据），再追加一条包含该 `prompt`、同号 RGB 图片与深度规则文本的多模态消息，交给**同一个** VLM 的下一次请求。工具内部不调用模型，不把原图/base64 写入工具结果或日志。RGB 取得但深度缺失、错配或无效时，仍把 RGB 与 `depth_valid=false`、未知前方距离如实送达；RGB 取不到时报告观察失败，按现有失败停止语义结束本轮。一次模型回复仍至多执行一个工具调用，`observe` 也计入上限和历史预算。

**动作后与深度上限。**任何实际位移或非零转向完成后，不自动给 VLM 取图，并清除动作前的 `ToolContext.observation/depth_rules`，使旧画面和旧数值不再冒充当前位置；`forward` 返回“未移动”时没有实际位移，不因此清除当前视觉观测。系统提示词明确建议**每次移动后优先调用 `observe(prompt)` 查看周围变化**，但这只是视觉规划建议，不是 `forward` 必须先调用 `observe` 的门槛。无论模型此前是否调用过 `observe`，每次仿真 `forward(distance_m)` 都先检查正的有限参数，再从现有 controller 等待**采集时间晚于本次工具调用开始**的新 RGB-D 配对，按现有 20 米视距、相机几何和 1 米计划余量重新生成仅供本次动作使用的深度规则；VLM 的正常思考耗时不会让先前图像直接授权前进，也不额外调用 VLM。程序以 `min(请求距离, 19 米, 本次 forward_max_m)` 下发正向距离；前缘障碍约 1.5 米时最多约 0.5 米，1 米内为 0 米。请求超限时仍正常执行缩短后的距离，在工具结果中回报请求值、指令值、障碍/净空和缩短原因。新 RGB、深度、内参、时间配对或几何规则任一缺失/无效/超时，就**不发前进目标，执行 0 米**，以正常“未移动”结果告诉 agent 原因；不得退回单次 19 米盲飞，也不得把无回波或未知像素伪作空地。本次工具采到的 RGB 只用于深度配对，**不会自动作为图片发给 VLM**；模型想看画面仍需调用 `observe(prompt)`。19 米仅是单次固定上限，不保证最终净空或制动性能。实机 `forward` 维持现有有效深度、原 0.2 米限额和逐动作 HITL，不借仿真逻辑放宽。

## 0. 目标、解释与边界

目标是把**人工给定的一个目标**交给一个持续运行的 `drone_harness`：每轮取得时间匹配的新 RGB-D，程序产出简短深度规则和数值安全上限，同一个多模态 VLM 看 RGB、读规则并用原生 function calling 提议**至多一个**短飞行动作；程序检查、执行，再自动补入动作后的新观测。双入口改名为 `drone_harness_sim`、`drone_harness_real`，保留各自 profile 及 PX4/MAVROS 安全链。真机入口只做配置/HITL 桩件验证，不进行真机自主飞行。

用户第 6 步的“单一 VLM 模型进行规划、工具调用与多模型”按已确认方案理解为“**单一多模态 VLM**”：图片理解、文本规划、function calling 在同一模型/服务完成，不接第二个视觉模型。本阶段不擅自增加模型。

“每次 `agent_loop` 前注入”有两个时点：新目标进入 `agent_loop` **之前**注入首个观测；同一个 `agent_loop` 内每次成功的非终止动作之后、**下一次 VLM 请求之前**再注入动作后的新观测。只在下一次交互式 runtime 调用前注入，会让一次 function-calling 循环里的后续决策继续看旧图，不满足闭环要求。这里的“同一帧”指 RGB 与深度来自**经时间阈值配对的同一次观测**，而不是两个 ROS topic 必须有完全相同的时间戳。

**2026-09-25 时序与安全边界修订。**一次规划使用观测 A：采集 A 时 RGB-D 必须同步、来源有效，程序算出并冻结 A 的 `DepthRules.forward_max_m`。VLM 正常思考数秒（实测约 7 秒）不使 A 因 1 秒帧龄自动失效；模型返回动作后**不专门取观测 B、不重新计算深度上限、不再次调用 VLM**。`forward` 起步前只对 A 的有效性标记、有限正数距离和 A 数值上限/profile 固定限额做一次检查，然后调用原项目的 `move`。短动作完成后才取采集晚于动作结束的观测 C，把 C 的 RGB 与同帧深度摘要发给 VLM。受控仿真假设 VLM 思考时无人机悬停、动作期间障碍不移动；不新增运动中逐帧深度/障碍守卫，也不能宣称动态障碍避让或深度断流即悬停。原 `move` 的位姿、状态、超时、中断和 PX4 安全处理保留。初次取 A、动作后取 C 时仍检查传感器采集新鲜度；该阈值**不是**模型思考或人工确认的期限。

## 2. 跨阶段接口合同

这些是实现时须保持稳定的**数据关系**，不要求为每一项新增类。优先复用现有 `ToolContext`、`TaskState`、工具返回 `dict` 和日志函数；仅为 RGB-D 观测及规则增加确有需要的数据容器。

| 合同 | 最少字段/行为 | 失效时 |
|---|---|---|
| `ObservationSnapshot` | `observation_id`、RGB 内容、深度数组、各自采集时间、接收时间、相机标定、位姿/状态快照、同步/新鲜度标记 | RGB 不可用则停止本轮；深度不可用可形成显式失效摘要 |
| `DepthRules` | 与快照相同的 `observation_id`、`depth_valid`、`front_clearance_m` 或未知、`forward_max_m`、左前/右前可见障碍或未知、原因 | 不可信时 `forward_max_m=0`；不能沿用旧深度 |
| 现有 function calling | 原生的一个 `takeoff/forward/rotate/land` 调用，或零调用文本；沿用现有 tool-result `dict` | 多调用整体拒绝；未知/坏参数零执行；失败后不继续飞行 |

安全检查直接在现有 `runtime/tool_dispatcher.py` 和 `tools/flight.py` 的调用边界完成，读取 `ToolContext` 中与当前 VLM 输入绑定的 A 观测规则、`profile.safety` 和 controller 状态；结果写入现有工具日志。**不另造 `SafetyDecision`、`ActionProposal`、`ActionResult` 三套对象或第二个调度器。**

成功的非终止动作之后，消息顺序固定为 `assistant.tool_calls(1) → tool 结果 → 新的多模态 user 观测 → 下一次 VLM 请求`。`land` 成功即结束；模型零调用的“候选完成”只是候选，必须独立核验且不会自动触发 `land`。长任务只保留当前目标、最近动作结果、步骤/观测编号、连续拒绝/无位移计数及有界消息历史，不引入第二阶段的任务队列。

## S3. 输出 RGB-D 结构化规则和前进数值上限

**采集与配对。**在现有 `px4/controller.py` 节点上增加最小的深度/相机参数订阅，用小型 `runtime/observation.py` 辅助缓冲/配对，**不另建 ROS 节点**；继续使用现有后台 ROS executor，让原 setpoint timer 在等图和 VLM 时运行。回调只做解码、时间标记和有界缓冲，不做耗时模型请求。按同一 ROS 时钟域的 header 时间配对 RGB 与深度；在取 A 或动作后取 C 时检查最大配对时差、采集帧龄、缓冲大小和等待超时；同时记录单调时钟接收时间以测等待耗时。采集帧龄阈值不用于限制随后 VLM 的思考时长。动作后新观测必须能证明其**采集**晚于动作结束，不能仅因旧帧“晚收到”就视为新帧；时钟域不可比较则停止该轮。缺深度可返回带错误码的 RGB 观测，但不伪造可前进距离。

**几何与摘要。**`vision/depth_rules.py` 校验实际编码和单位，NaN/Inf/零值仍为未知；仅在透视射线米制语义及远值/无命中含义验证后，有限正值 `>20 m` 可按“该射线在 20 m 内未见表面”的**下界**截为 20 m，不能宣称测到了更远的净空。不再要求全图每个像素都落在 `(0,20] m`，也不使用全图覆盖率硬门；投影到前进通道的未知像素仍给零前进上限，不能只取中央单像素或把缺测当空地。当前相机的近场通道投影可能覆盖整张图，因此取消全图数值上限硬门**不等于**允许任意 NaN/零值缺测。`front_clearance_m` 定义为**机体前缘到最近可信障碍的净空或保守下界**；`forward_max_m = max(0, min(profile.forward_step_limit_m, front_clearance_m - 测量余量 - 制动/超调余量 - 延迟余量))`，机体前缘偏移已体现在净空定义里，不重复扣减。当前仿真独立正向限额 19 米，真机仍使用原相对位移限额。

## S4. 修改 runtime：自动注入观测、轻量状态与提示词

**输入。**S3 的观测/规则合同通过；本步只用假 VLM 和假动作结果验证消息循环，不启动实际运行入口。保留一个持续运行的 runtime，不改成“每动作重新启动 runtime”，也不把拍照变成模型工具。

**首轮注入。**新目标到来时，`runtime/runtime.py` 先建立该目标自己的消息上下文：按当前 profile 生成 system prompt、当前目标和首个 `ObservationSnapshot`。RGB 用服务支持的图片内容格式直接放进多模态 `user` 消息；同一观测生成的深度摘要以文本放在**同一条**消息中，带 `observation_id` 和采集时间。没有有效 RGB 时不调用 VLM。深度失效时可发送 `depth_valid=false; forward_max_m=0; reason=...`；程序仍禁止发布正向前进目标，仿真误提议只返回“未移动”。

**动作后注入。**`runtime/agent_loop.py` 一次只接受 0 或 1 个工具调用。合法单动作的结果按协议追加为 `tool` 消息；如果它是成功的非终止动作，立刻等待**采集晚于动作结束**的新 RGB-D，并在下一次模型请求前追加新的多模态 `user` 消息。若动作失败、等待新 RGB 超时、用户中断或控制状态不可信，结束本次自主循环，不拿动作前的画面继续规划。若 `land` 成功，不再调用导航 VLM。若模型返回多个 `tool_calls`，**任何一个都不执行**；若决定保留该回复在历史中，就为每个 call ID 写入拒绝结果保持工具协议配对，否则丢弃这次回复并结束该轮。

**消息与状态预算。**一个人工目标对应一个有界对话；runtime 可继续接下一条人工输入，但不能把上个目标的图片无限继承。保留 system、目标、当前观测、上个动作及其成对的工具结果、必要的简短状态；旧图片与冗长原始返回移出 `messages`，日志可留去敏元数据。扩展 `runtime/task_state.py` 记录 `observation_id`、step_id、最近动作实测结果、连续拒绝/无有效位移次数及最大轮次。所谓“无进展”第一版只依据可核对的动作失败或位姿无变化计数，不把 VLM 自报“接近目标”当安全事实；超过预算就安全停止。

**提示词内容。**拟更新 `llm/prompts.py`，明确：只处理当前单目标；RGB 用于识别，距离/净空以程序深度规则为准；仅 `takeoff/forward/rotate/land`，每次最多选一个；每次动作后等待工具结果和新观测再决定；深度无效/未知、看不清或图文矛盾时不得前进；不得虚构视野外/背后/着陆区安全；不调用检测、追踪或 skill；疑似到达时**不调用飞行工具**，只用文字报告“候选完成”和可见证据。提示词是行为引导，不代替程序限额或授权。

**拟变更位置。**`runtime/runtime.py`、`runtime/agent_loop.py`、`runtime/task_state.py`、`llm/prompts.py`、`logging/task_log.py`；可以增加纯消息构造器，供离线测试。S4 不接真实客户端、不开 PX4。

**测试与证据。**拟增 `test/test_agent_loop_observation.py`、`test/test_message_compaction.py`：假客户端记录请求，断言 `首观测 → VLM → 单工具 → tool 结果 → 新观测 → VLM` 顺序；新观测确实晚于动作完成且 RGB/摘要同号；拒绝多调用之前执行次数为 0；无调用、候选完成、未知工具、坏参数、动作失败、RGB 超时、失效深度、用户中断、`land` 成功均有正确停止语义；长轮次下图片数和消息长度有界。现有 `test/test_mavros_sim_runtime.py` 的 setpoint/线程安全回归不能因改循环失效。

**通过/停止。**从假客户端记录能逐轮复原“A 观测—一次决策—最多一个动作—动作后 C 观测”；一个 runtime 内可连续多轮，且假控制器的命令计数仍为 0。任何路径在动作结束后仍拿 A 作为下一次规划观测、多动作执行或旧图无限累积，则停止修正，不进入 S5；模型正常思考数秒不算“旧帧续飞”。

## S5. 四动作安全门与原飞控安全链

**输入。**S4 的调用边界通过，S3 给出与 A 观测号绑定的数值上限；先复核原 `flight.move` 的参数、位姿、飞行状态、超时、人工中断与 PX4 安全处理。本步历史提交曾增加运动中守卫；S7 按本文修订移除其新增部分，不改写 S5 已有提交。

**四动作表。**

| 模型动作 | 参数与执行前检查 | 底层执行和终止 |
|---|---|---|
| `takeoff(height)` | 沿用现有有限正值、高度限额、起飞状态/电池/PX4 就绪检查 | 原实现不重写；成功后再取新观测 |
| `forward(distance_m)` | 正向距离有限且为正、A 与规则同号；仿真请求超限自动缩短，零上限不发前进目标；真机超限或无效深度仍拒绝 | 仿真正指令包装原 `flight.move(context, commanded_m, 0, 0)`，不传运动中深度守卫；返回后再取 C |
| `rotate(direction,degrees)` | 沿用现有方向、有限角度、profile 限额、位姿/飞行状态检查 | 原实现不重写；转向后须取新观测再前进 |
| `land()` | 在原位姿/飞行状态/PX4 确认前提上加明确降落授权；候选完成不等于授权 | 原实现不重写；成功为终止动作 |

**最小新增检查。**不创建 `SafetyDecision` 类或第二套调度器；`forward` 包装器读取 `ToolContext` 中与 A 同号的 `DepthRules`，并复用现有 `is_finite_number` 和 `profile.forward_step_limit_m`。零/负、布尔值、NaN/Inf 和 A 与规则错号拒绝；仿真超限会明示请求/指令值并缩短，深度未知或上限为零返回正常“未移动”但绝不发前进 setpoint。真机保持深度无效或超限直接拒绝。A 通过采集检查后不因 VLM 正常耗时而被动作门拒绝，也不要求控制器当前缓存帧与 A 同号。原 `move()` 仍负责位置、航向、机体系换算、飞行状态和超时检查。VLM 只见 `forward`，无法给底层 `move(x,y,z)` 设置 `y/z`、后退或侧移。明确降落授权可在现有 `TaskState` 中用一个状态位或本次人工确认承载，不新增授权服务，也不从 VLM 的“候选完成”推断。真机沿用 `runtime/tool_dispatcher.py` 的四动作 HITL，无 `rotate/land` 豁免；批准仍绑定动作、参数、A 观测号和明确授权，不能覆盖 A 上限与原 PX4 状态检查，但不按等待期间的帧龄取 B 或重算 A 的深度。真机深度保持未验证，本阶段不进行真机飞行。内部应急悬停、RTL/失控保护不等待模型或 HITL。

**复用原 `move()`。**`forward` 通过一次 A 上限门后直接调用不带 `guard` 的原底层移动；撤销 S5 新增的发布前/运动中深度守卫及其专用中断分支，不加监视线程或独立安全控制器。保留原 `move()` 的固定距离、姿态/位姿、目标高度、超时、人工中断与原 PX4 安全路径。原 0.3 m 到达容差会让 0.2 m 短步在起点误判完成，因此只为 `forward` 传入不大于 0.05 m、且小于请求距离一半的完成容差，不改变其他底层 `move` 调用。运动中若深度断流或静态场景假设不成立，本阶段**没有**基于深度的自动急停能力，验收文案和日志都不能宣称具备它。

**S7 修订位置。**重点改 `tools/flight.py` 的 `forward` 一次 A 上限门、去掉 `move()` 新增 guard hook，并调整 `runtime/tool_dispatcher.py` 的观测帧龄/HITL 判断；其余四工具 schema、registry、原 PX4 控制器 setpoint/Offboard 逻辑维持已通过的实现。不增加新的安全模块。

**测试与证据。**在 `test/test_forward_gate.py`、`test/test_real_hitl.py` 和原安全回归中验证：A 采集时无效/错号、负数、零、NaN/Inf、超 A 上限或 profile 限额都在发目标点前拒绝；假 VLM 延迟 7 秒以上时，有效 A 不因帧龄独自被拒，且没有额外 B/第二次 VLM 请求；`forward` 底层恒为 `y=z=0` 且不再传深度 guard。原 `move()` 的位置/状态、超时悬停、人工中断、PX4 拒绝和 Offboard-loss 交接测试继续运行；S5 的专用运动中深度守卫测试须改为与新合同相符的断言，不能悄悄删除以换取绿色。真机四动作 HITL 无豁免，未经批准不得执行；本阶段没有真机飞行测试。

**通过/停止。**四动作可见面恰好匹配设计，真机四动作 HITL 全覆盖，A 上限门对无效与超限输入 fail-closed，原超时/中断和 PX4 安全回归通过。任何超限仍可执行、A 无效仍前进或 HITL 被绕过，均不得进入仿真自主前进；不再把运动中深度断流悬停列为本阶段能力。
