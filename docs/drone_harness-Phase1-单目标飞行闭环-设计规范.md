# `drone_harness` 阶段 1：单目标飞行闭环（架构设计）

> 面向后续实现 AI 的设计规范，2026-09-25 修订。本文只定义目标、边界、架构和验收；阅读或更新本文不等于获得代码实施、创建 GitHub 仓库或启动仿真的授权。

## 1. 阶段目标

把当前 `drone_agent` 改造成**一个 VLM 驱动的单目标飞行闭环**：无人机每次取得新的前视 RGB-D 观测，程序把深度信息压缩为可靠的短文本，VLM 同时完成识图、当前目标判断和下一步规划；程序检查安全条件后，只执行一个短动作，再重新观测。保留**一个持续运行的 runtime 与原生 function calling 形式**，不是每执行一个工具就重启 runtime。

阶段 1 只接受**人工给定的一个目标**。它不拆分长导航指令，也不自动切换下一个目标；这些属于阶段 2。因此阶段 1 可以单独实施和完整验收。

## 2. 新仓库与现有项目的关系

后续实施时，在用户自己的 GitHub 账户中创建名为 **`drone_harness`** 的独立仓库，作为本次改造项目的存放处。仓库可见性原默认 private；用户于 2026-09-25 明确决定改为 public。创建前须核实登录账户与仓库是否已存在，不能覆盖同名仓库；首次公开推送前必须审查待提交文件、密钥和运行资产。

新仓库以**当前 `drone_agent` 的实际工作内容**为起点，在一个新的独立工作目录中迁移和改造。现有本地 `drone_agent` 始终作为只读来源：不编辑、不清理 dirty 文件、不重置、不提交、不改远端。迁移时审查来源内容，不能把密钥、日志、图像、运行资产或无关仓库推到 GitHub。

用户于 2026-09-25 追加统一命名要求：**新仓库中的项目、Python/ROS 包、可执行入口、配置位置及当前运行文档均改用 `drone_harness`**；对应入口为 `drone_harness_sim`、`drone_harness_real`，保留原有仿真/真机双 profile 和调用链，不保留模型可见的旧工具作为兼容入口。来源仓库路径、原提交及 S1 迁移记录中的 `drone_agent` 是历史事实，不能改写。两个入口共用单目标规划链，但真机 profile 的限制更严格；阶段 1 仅对离线和仿真闭环验收，不据此宣称真机自主导航已获准使用。

## 3. 核心架构

```text
人工给定一个目标 ─────────────────────────────┐
前视 RGB 图像 ────────────────────────────────┤
深度图 → 程序几何解析 → 简短距离/净空文本 ────┤→ 单个 VLM
上一次动作结果 ────────────────────────────────┘      │
                                            function calling 决策
                                                       │
                                              程序安全门检查
                                                       │
                                   起飞 / 前进 / 旋转 / 降落，至多一个
                                                       │
                             工具结果 → 自动注入新 RGB + 深度摘要 → 下一轮
```

这里的深度解析器、安全门、日志器都是**普通程序模块，不是额外的 Agent**；每个决策轮只调用一个 VLM。RGB 作为图片直接给 VLM，不先转文字；深度图不直接交给 VLM 猜距离，而是由程序转成有单位的短摘要。两者必须来自时间匹配的一次观测，不能把新 RGB 和旧深度拼接。

一次 runtime 可包含多次 VLM API 请求。首次请求前，程序自动加入初始 RGB 与对应深度摘要；一个非终止飞行动作的 `tool` 结果写入后、下一次请求前，程序自动加入动作后的新观测。此时模型继续使用 function calling 决策，**不新增模型可见的拍照、观察或深度查询工具**。提示词要求依据最新观测规划，但实际获取、配对、注入和失效处理均由程序承担。

运行时只维护当前目标、最近动作及其实际结果、步骤/观测编号、连续无进展或连续拒绝次数等轻量任务状态；这用于给 VLM 提供简短上下文、识别卡住并形成逐轮可核对日志，不是阶段 2 的任务队列或语义地图。现有 PX4 setpoint 发布、人工中断和应急处理在等待 VLM 或新观测期间仍须运行。

### 各层职责

| 层 | 应负责什么 | 不应负责什么 |
|---|---|---|
| 观测层 | 获取同步的 RGB、深度、位姿和飞行状态；标记数据是否新鲜、可用 | 不替 VLM 判断目标语义 |
| 深度摘要层 | 校验深度单位与标定，估计前方机体可通行净空、给出本轮安全前进上限 | 不调用另一个视觉模型；不凭单像素断言前方安全 |
| 单 VLM 决策层 | 看 RGB、读当前目标与深度摘要，沿用 function calling 调用一个飞行工具，或不调用工具并说明进展 | 不直接控制 PX4；不凭 RGB 猜精确米数；不自行改安全限制 |
| 程序安全门 | 检查授权、飞行状态、传感器有效性和动作参数；拒绝或缩短不安全动作 | 不把安全判断外包给提示词 |
| 执行与记录层 | 复用现有飞控动作、安全悬停/应急处理和日志；动作完成后取得新观测 | 不连续执行同一轮输出的多个动作 |

## 4. VLM 输入、输出与提示词

每轮模型输入保持精简：固定 system prompt、**当前一个目标**、最新前视 RGB、同次观测生成的深度摘要、上次动作的简短结果。不传完整历史、原始深度图或旧视觉检测/追踪输出。长时间运行时，应压缩已完成的旧轮次，只保留必要的最近工具调用/结果配对和轻量任务状态，不能让旧图片无限累积在 `messages` 中。

规划器必须是**同一个同时支持图片输入与原生 function calling 的 VLM 服务**。现有文本 LLM 主循环与 `analyze_view` 的独立 VLM 调用不能并存于新闭环；实施前要用离线兼容性测试确认所选服务能在同一次请求中接收 RGB 图片、规则文本和四个工具 schema。

深度摘要示意：`深度有效；正前方可通行净空约 2.4 m；本轮最多前进 0.5 m；左前近障。` 第一版只需把 `observation_id`、`depth_valid`、`front_clearance_m`、`forward_max_m` 和可见的左前/右前障碍或未知状态组成短的键值文本；前方净空不是目标距离，也不证明侧方安全。深度缺失、不同步、过期、单位/标定不明或覆盖不足时，应明确写成 `depth_valid=false；forward_max_m=0；原因=...`，不能拿旧深度补齐。摘要只是给 VLM 理解场景；**安全门仍使用程序持有的数值和有效性标记**，不能只读模型回复里的距离。

**保留现有 function calling 方式**，不引入新的 JSON 决策协议：VLM 要么调用 `takeoff`、`forward`、`rotate`、`land` 中的一个工具，要么不调用工具并用简短文字说明“不确定，暂停”或“候选完成”。阶段 1 不需要机器解析任务切换状态。

system prompt 应明确：只处理一个目标；RGB 用于识别，测距以深度解析为准；**每次只调用一个飞行工具，等待动作结果与更新的 RGB-D 后再决定下一步**；不得在同一回复中批量规划或调用多个动作；看不清或有矛盾就不前进；不得虚构视野外信息；不得调用额外检测、追踪或 skill。目标疑似到达时不再发飞行工具调用，只报告“候选完成”和证据，不能把自己的判断当成已验证事实。

“一步一观察”由**提示词行为要求 + 程序自动注入观测**共同完成，不是把 function calling 换成另一套接口。为防止模型偶尔违反提示词，运行时仍须做最小防呆：同一响应出现多个飞行 `tool_calls` 时，在执行第一个前全部拒绝；合法的非终止单次调用完成后，下一次模型请求前必须取得更新的 RGB-D，不能沿用动作前的画面。这只是调用边界校验，不增加第二个模型或规划器。没有工具调用就不移动，并暂停本次自主执行或报告候选完成。

消息顺序固定为：初始多模态 `user` 观测 → `assistant.tool_calls`（至多一个）→ 对应 `tool` 结果 → 动作完成后采集的新多模态 `user` 观测 → 下一次 VLM 请求。新观测必须带观测编号和可核对的采集时间；RGB、深度之间的时间匹配，以及“采集晚于动作完成”，都由程序检查，不能混用不可比较的时钟。若动作失败或等待新 RGB 超时，则不再调用 VLM 继续飞行；若新 RGB 有效但深度不可用，可以传入明确的失效摘要，但程序必须禁止 `forward`。`land` 是终止动作，不再启动下一次导航决策。

## 5. 只保留四种模型可见飞行动作

| 动作 | 行为边界 |
|---|---|
| `takeoff` | 在已有起飞安全条件通过后升至受限高度 |
| `forward` | 只沿机头方向短距离前进；不能后退、侧移或改变高度 |
| `rotate` | 在当前位置左右旋转受限角度，转向后才能继续前进 |
| `land` | 仅在明确授权且降落条件满足时执行；“候选完成”不能自动触发降落 |

实现策略是**保留现有飞控和安全机制，收窄 Agent 可调用的动作面**。旧的多轴移动能力可作为内部底层实现，但 VLM 只能提出正向前进距离；程序保证侧向、后向和垂直分量不可由模型设置。`forward(distance_m)` 只接受正数，并在程序内以机体系前向距离调用底层移动，侧向和垂直分量固定为零。每次模型回复至多执行一个动作；非终止动作等待结果和新观测，`land` 成功后结束闭环。同一回复中的多个调用不能逐个执行。

新仓库应删除不再需要的模型工具与相关运行链：额外状态查询/计时/拍照分析工具、独立的视觉检测、目标追踪、skill 激活及其无消费者代码和配置。删除之前先检查依赖；**状态监控、人工中断、悬停、返航/失控保护等内部安全能力必须保留**，只是不能作为 VLM 自由调用的工具。不能为精简而重写或削弱已有 PX4 安全链路。

## 6. 安全与“目标完成”边界

- 深度无效、过期、单位/标定不明、前方净空不足时，**绝不盲目前进**；必要时保持位置或进入现有安全悬停路径。
- 安全前进上限由程序根据深度、机体尺寸、安全余量、制动/控制超调余量和已有飞行限制计算，例如取 `min(profile 单步上限, 已确认前方净空 - 各项余量)` 后再保证非负。未知区域不能当作畅通；具体余量需在仿真中标定，不得凭提示词确定。VLM 只能选择不超过本轮上限的距离；超限请求拒绝并记录，不默默裁剪。执行前重新检查有效性，移动过程中若观测变坏，应中止并走既有安全处理。
- 网络/VLM 失败、输出不可解析、位姿或飞行状态不可用、动作超时、PX4 拒绝或用户中断时，不继续执行后续动作，并记录原因。
- 保留仿真/真机双入口，统一命名为 `drone_harness_sim` 与 `drone_harness_real`；真机 profile 的 `takeoff`、`forward`、`rotate`、`land` 每次模型调用均须 HITL；当前 `rotate`、`land` 豁免不能带入新实现。人工批准绑定当次动作、参数与观测；等待批准后如观测过期或限制变化，须重新检查，批准不能覆盖安全门。内部紧急悬停、失控保护和返航等安全处理不等待 VLM 或人工批准。
- 前视 RGB-D 不能证明全向无障碍、头顶安全或着陆区安全。阶段 1 的自动导航只在离线/仿真场景验收，不能据此放行真机自主飞行；真机相机话题、标定和保护须另行验证，不能沿用仿真相机配置假定其可用。
- VLM 不调用工具并明确报告“候选完成”时，阶段 1 停止继续自主前进并保留证据；目标是否真的到达由独立仿真真值或人工复核。阶段 1 **没有**任务队列，也没有“切换下一任务”的状态机。

## 7. 独立验收标准

1. 新仓库确实为 `drone_harness`，包含从当前项目受控迁移的实现；原本地 `drone_agent` 的内容、dirty 状态和 Git remote 未被改动。
2. 离线调用记录证明仍使用 **function calling + 一个支持图片的 VLM**：首次请求带初始 RGB/深度摘要；成功的非终止动作的 `tool` 结果之后、下一次请求之前，自动带入动作后采集且时间匹配的新 RGB/深度摘要。不再出现 `analyze_view`、独立目标检测或追踪调用；旧图片不会无限累积。
3. 模型可见飞行动作恰好四种；非法或同一回复中的多动作请求在执行前被拒绝；不存在模型可触达的侧移、后退或任意高度移动。`forward` 超过当轮程序上限时被拒绝，实际飞控命令的侧向和垂直分量恒为零。
4. 深度缺失、过期、不同步、前方障碍、RGB 超时、VLM 失败、动作失败等离线回放用例均不产生后续危险动作；原有中断、超时、悬停和 PX4 安全回归仍通过。`drone_harness_real` 入口保留，四个模型飞行动作的 HITL 均生效，但本阶段不以真机飞行作为验收。
5. 在**一个**仿真目标上完成“起飞 → 观察 → 旋转/短步前进 → 候选到达或安全停止”的可复核闭环。日志能对应每轮观测编号、深度摘要、工具调用、安全门和动作结果；目标到达不能只凭 VLM 自述判定。

本阶段验收不依赖长指令拆分、任务切换、语义地图或复杂局部路径规划。它们应在后续阶段分别设计、分别验收。

## 8. 分阶段实施约束

改造幅度较大，详细实施文档必须拆成可独立测试和验收的里程碑，不能把仓库迁移、感知、模型、飞控安全和仿真端到端改造一次性提交。建议的依赖顺序为：受控迁移与基线 → RGB-D 观测 → 简单深度规则 → 单 VLM function calling 与自动注入 → 四动作安全门及真机 HITL → 离线回放和单目标仿真闭环。每个里程碑都须写清输入前提、只修改哪些相关模块、可自动执行的测试、人工检查点、通过标准和失败时的停止条件。前一里程碑未验收，不得以后一里程碑的仿真成功掩盖它的失败；阶段 1 不安排真机飞行验收。
