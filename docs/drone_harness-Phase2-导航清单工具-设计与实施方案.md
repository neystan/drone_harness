## 1. 目标与取舍

用户输入一次长导航指令，同一个 VLM 自主建立计划、选择原有飞行工具、判断子目标完成并调整计划，正常情况下不需要用户逐段介入。

采用一个 `update_navigation_plan` 工具提交完整清单。程序保存状态、展示进度并维护原有执行保护；提示词保持简短，不另加评审模型、子 agent 或语义校验器。

本轮已选择轻量方案，不采用“冻结初始目标和完成条件”的严格状态机，也不采用单独的模型完成核验请求。少硬规则意味着计划理解、完成判断及改写质量仍依赖 VLM，必须通过后续模型回放和真实仿真评估，不能承诺必然到达。

仅调整阶段 2。原八工具、PX4 控制器、深度前进限制、动作后等待、人工介入、安全交接、模型连接配置均不重构。实机不开放新计划工具；原 `drone_agent` 不修改。不增加地图、持久任务队列、重启恢复或新依赖。

## 2. 工具接口

工具名：`update_navigation_plan`。

参数：`subgoals`、`finish_action`、`reason`，均必填。每次提交完整清单，不是局部补丁；没有计划时创建，有计划时替换。

示例用户输入：“起飞飞到前方路灯附近，再沿道路到停车场入口，最后降落。”

```json
{
  "subgoals": [
    {
      "id": "g1",
      "description": "起飞并飞到前方路灯附近",
      "completion_condition": "已起飞，当前观察支持已处于指定路灯附近，而非仅远处可见",
      "status": "in_progress",
      "evidence": ""
    },
    {
      "id": "g2",
      "description": "沿道路到停车场入口",
      "completion_condition": "识别停车场入口，当前观察支持已抵达入口附近",
      "status": "pending",
      "evidence": ""
    }
  ],
  "finish_action": "land",
  "reason": "按用户要求建立两段导航计划，抵达后降落"
}
```

| 字段 | 含义 |
| --- | --- |
| `id` | 本轮清单内唯一的字符串标识；提示模型为同一目标保留 ID |
| `description` | 要完成的导航段，不是预先固定的逐步动作列表 |
| `completion_condition` | 模型判断完成的文字条件 |
| `status` | `pending`、`in_progress` 或 `completed` |
| `evidence` | 模型填写的简短完成依据；未完成通常为空 |
| `finish_action` | 复用 `land` / `hold`；降落不重复列为子目标 |
| `reason` | 本次创建、推进或改写的简短原因 |

不增加 `source_instruction`、目标分类、依赖图或模型可写的整体成功字段。原始用户指令由程序另存，不由工具参数覆盖。观测编号和时间戳仍只用于内部记录。

## 3. 提示与硬规则的边界

### 3.1 简短提示

仿真阶段 2 的计划相关系统提示建议为：

> 导航任务开始时，使用 update_navigation_plan 建立简洁的有序计划。依据观察与实际工具反馈执行，完成当前目标后及时更新进度并填写简短依据；必要时调整未完成计划，但保持用户原始目标和约束。不确定是否完成时继续获取信息。清单更新不代替实际飞行动作。普通交流和单步动作无需建立计划。

工具说明只补充接口用法：

> 创建或替换本轮完整导航清单；每次包含所有仍需保留的条目。同一目标沿用 ID，通常只将当前执行项设为 in_progress。仅在计划或进度变化时调用。finish_action 默认 land；用户要求保持空中时使用 hold。

其余安全、观察、动作后等待和收尾提示复用现有内容，不重复写进计划提示。移除旧的“只输出完成判断 JSON”“不允许改写子目标”等冲突指令。

### 3.2 最小硬校验

- 参数必须是合法对象，字段、类型与枚举符合工具定义，不接受未知字段。
- `subgoals` 是非空列表；ID 唯一；ID、描述、完成条件、更新原因是非空字符串；`evidence` 是字符串，允许空字符串。
- 最多一个 `in_progress`，避免同一架无人机出现两个明确的当前项。不强制存在一个当前项；没有时以首个 `pending` 作为上下文中的待选焦点，不偷偷改写模型提交的状态。
- 完整校验候选清单后一次性替换内存状态；失败保留旧清单。
- 沿用每次模型回复最多一个工具调用的限制；计划更新与飞行动作不能同轮执行。

不新增以下硬限制：冻结初始 ID、禁止删除/调序、冻结完成条件、禁止重开已完成项、一次只能完成一项、强制非空完成依据、固定子目标数量或额外计划修正次数上限。

旧阶段 2 的“有当前配对观测才允许推进”硬门不移植到清单写入工具。基于最新观察确认完成改由提示指导，工具如实记录模型判断。动作后原观察仍会失效，并继续向模型提示需要重新观察；飞行工具的 RGB-D 获取、深度限制及安全校验不变。此项放宽的是完成记录条件，不是飞行动作权限。

这些选择允许模型误判、漏拆或改错计划；不能将格式合法当作任务语义正确。后续只针对实际出现的问题补充约束。

## 4. 执行流程与运行状态

```text
用户输入
  → 原 agent 工具循环（不再单独请求分类/拆分）
  → VLM 按需 observe / get_state，并调用计划工具建立清单
  → VLM 选择原飞行工具执行
  → 依据反馈继续执行，或调用同一计划工具推进/改写
  → 清单全部完成后执行原降落/悬停收尾
```

“导航先建计划”是提示要求，不新增自然语言分类器或未建计划时的运动拦截器。普通聊天和单步动作仍可直接使用原循环；如果模型遗漏建计划，程序不会凭关键词替它建立清单，此行为应在模型回放中检验。

启用仿真阶段 2 时暴露第九个工具；未启用阶段 2 或实机仍为原八工具。分发层也检查启用条件，不能只靠隐藏 schema。新工具不是飞行工具，不触发动作后等待，不计入平移动作进展，不清空有效观察、不重置无位移计数。

计划保存原始指令、完整条目、收尾动作和最近更新原因。条目状态以模型提交为准，不再由单调递增的 `current_index` 生成。完成数量按实际 `completed` 项统计；当前项优先取唯一 `in_progress`，否则显示首个待执行项并注明尚未指定执行项。

任务状态仍使用 `running / finishing / completed / incomplete`：

- 非空清单尚有未完成项：`running`。
- 非空清单全部标记完成：`finishing`，不等于整体任务成功。
- `land`：模型调用原降落工具，成功且清单全部完成、收尾要求为 land，才记录 `completed`。提前降落记录 `incomplete`。
- `hold`：复用现有空中状态、模式与悬停交接确认，确认成功才记录 `completed`。
- 停止、超时、用户介入或预算耗尽：记录 `incomplete`，沿用原安全处理。

`finishing` 且尚未结束时仍允许计划工具纠正清单；出现未完成项则回到 `running`。保留原收尾阶段对导航运动的限制，允许状态查询与原降落；新增计划工具作为纠正入口。hold 的确认收尾仍由程序立即执行，不另设模型请求。

原始指令与实际结果不由模型清单覆盖；`completed` 的用户说明仍为“模型已确认导航段，收尾完成，未独立核验到达”。

## 5. 更新结果与异常

成功时返回 `success=true`、`changed`、完成数量、总数、当前项标识、任务状态及简短说明。`success` 只表示清单更新被接受。同一清单的重复提交不触发重复推进、重复压缩；工具调用日志仍保留。

参数解析或清单基本校验失败，返回 `success=false`、错误码、具体原因和 `plan_changed=false`，让模型修正；不将失败候选写入状态。仅计划工具的这类预期校验错误可继续循环。

其他工具失败、模型请求异常、程序异常及原安全退出维持原行为，不做全局重试策略变更。未建立计划时最多 50 次模型请求；首次成功建立计划后总上限为 200 次，计数从本轮第一次请求开始，包含建计划前的调用。改写、纠错、重新标记都不重置预算，也不新增模型连接自动重试。

有活动计划时，普通文字回复不自动结束本轮；程序以一句短反馈提醒继续工具执行。没有计划时普通文字仍可结束普通交流。旧的 `subgoal_complete` 文本解析全部退出正常执行链，自然语言内容不再作为计划写入接口。

## 6. 上下文、日志与终端

每次模型请求临时注入原始指令、最新清单、收尾方式、当前观察是否有效；旧快照不反复追加。没有计划时只提供简短计划工具使用提示。循环每次读取最新状态，不保留更新前的计划引用。

本轮仍保留实际工具反馈和最新一张观察图片。保留已有“完成一段后压缩”的能力，但只对纯推进更新触发：条目 ID、顺序、描述、完成条件及收尾动作不变，发生完成状态增加且没有重开已完成项；其余状态变化只能是选定下一执行项。改写、删除、调序、重开或拒绝更新不触发段落压缩。这只是内存优化判据，不限制工具是否接受计划。

压缩时保留原始任务及任务前对话、最新有效观察、本次计划更新调用和结果（完整成对），详细完成信息由最新清单承载。不得制造孤立 tool 消息。完整历史仍在原执行日志中；再次打开旧目标不恢复已经压缩的详细过程，模型可重新观察。

复用 `navigation_plan.jsonl` 和原工具日志。计划日志保存接受后的完整快照、更新原因及创建/更新/结束事件；旧快照不被覆盖。拒绝原因保存在工具日志。不新增任务持久化恢复；新用户轮次清空计划与观测，跨轮仅继承文字和简短进度摘要。

终端打印清单的待执行/当前/模型已完成状态、完成依据和本次更新原因。改写导致完成数量下降时如实显示，不强制伪装成单调进度。最终状态区分：工具执行结果、模型完成判断、独立到达核验。

## 8. 验证与验收依据

后续实施按“计划数据与工具 → 执行循环/提示/上下文 → 回归与文档”拆成小步，每步先补相关离线测试。具体实现任务安排在本设计审阅后确定。

### 离线测试

1. 完整创建、推进、插入/删除/调序、改写条件和重开目标均按模型提交保存；没有旧的冻结或单步推进限制残留。
2. 非法类型/枚举、空清单、重复 ID、多个当前项被拒绝且旧计划不变；工具校验错误后模型可继续修正。
3. 缺少新观察或 evidence 为空时，清单写入不被旧确认硬门阻止；仍明确只是模型标记，不能触发飞行或独立到达成功。
4. 没有单独拆分请求；自然语言加工具调用可以正常工作；活动计划普通文字不会提前结束；普通聊天/单步动作不强制建计划。
5. 计划更新不执行运动、不等待、不清观察、不重置无位移计数或请求预算；实机和未启用阶段 2 时拒绝新工具。
6. 新清单立即出现在下一次请求；动态创建计划后正确使用总预算；重复提交不会重复压缩；改写不丢当前段历史；所有工具消息完整配对。
7. 全部打勾但降落失败不能记录整体完成；提前降落不算完成；原 hold 状态检查与安全交接不放宽。
8. 保留原深度缩短/不移动、连续动作恢复、动作后等待、人工介入等阶段 1 回归覆盖。

### 后续模型与仿真验证（不在本次设计工作中执行）

离线假模型测试只能验证程序契约。另用授权后的真实 VLM 回放检查：初始拆分是否漏目标、是否主动创建清单、是否把远处可见误判成到达、遇阻是否合理改写、是否反复改计划而不行动。再按用户授权进行真实仿真，保存新版运行日志。

模型回放和仿真分别报告任务理解、模型标记完成与实际执行结果；独立到达需要另有环境证据。保留“系统正常运行”与“导航必然到达”的区别，不将阶段 1 离线通过或本方案离线通过当作实机安全验收。
